# Render Texture: Qt Scene into a Stride Texture2D

Status: planned (brainstorm 2026-11-14). Work: #116 QtTexture, #117 Clear pin, #118 MSAA, #119 QtTexture interaction, #120 QtRenderer [Stride]. Decision log for the node that renders a Qt scene offscreen and outputs a Stride `Texture`. Reference implementation: `SkiaTexture` in VL.Stride (`VL.Stride.Runtime/src/SkiaTexture*.cs`).

## Requirements (set by the user, 2026-11-14)
- Used like `Renderer [Qt]`, but opens no window; outputs a Stride `Texture` (Texture2D).
- Several such nodes in one patch must not block each other.
- Must not block Stride rendering; runs alongside it as smoothly as possible.
- Data stays on the GPU, no CPU readback (a second node or a pin may offer a readback path).
- Ownership and disposal thought through; no leaks.
- Transparency: a `Clear Color` pin like the Renderer; clear alpha 0 gives a transparent texture.
- Resolution as an `Int2` pin.

## Facts found (2026-11-14)
- VL.Qt references only `Stride.Core.Mathematics` (runtime excluded), not Stride.Graphics/VL.Stride, and runs on Linux.
- QtNative creates its own D3D11 device per process (`device.h`), shared by all Qt windows and image uploads; Qt runs the `basic` render loop on the main thread, pumped once per vvvv frame.
- `device-sharing.md` describes the QtNative device model; before this work it named Mode 1 (Qt on Stride's device) as the design, which the code never followed.
- Bridges in other vvvv libraries (VL.StandardLibs): `SkiaRenderer [Stride]` and `SkiaTexture` live in VL.Stride.Runtime, not in VL.Skia; `VideoSourceToTexture` in VL.Stride.Runtime, `VideoSourceToSKImage` in VL.Skia, VL.Video stays renderer-free; VL.ImGui is split into the documents/packages `VL.ImGui`, `VL.ImGui.Skia` and `VL.ImGui.Stride`.
- `SkiaTexture` has two renderers: `DefaultRenderer` (Stride's device, state swap) and `DedicatedRenderer` (own device, shared texture, shared `ID3D11Fence`s for write/read completion, GPU-side wait).

## Decided
- **Device (2026-11-14):** Qt keeps the QtNative device and renders into a texture shared with Stride's device; shared `ID3D11Fence`s order Qt's write and Stride's read on the GPU (like `SkiaTexture.DedicatedRenderer`). No CPU wait, Stride's context is never touched, Qt windows and uploaded images keep working. Rendering on Stride's device (Mode 1 of `device-sharing.md`) is rejected for now: Stride would own the device and the device-lost handling of QtNative would have to be rebuilt.
- **Same adapter (2026-11-14):** QtNative's device must sit on Stride's adapter (shared handles do not cross adapters); `vlqt_offscreen_bind` compares the adapter LUIDs. If they differ, log a warning and show the error at the node, never crash.
- **Adapter move (2026-11-14, task 1.5):** moving QtNative's device to Stride's adapter with `device::rebuild` works only while no on-screen window renders on it: Qt replaces a window's QRhi only after it noticed a device loss, so a window on a healthy device would keep the old device (and images of the new one would no longer draw in it). So bind moves the device (`device::moveTo`, like a loss: images upload again) while no window has a QRhi on it and no other scene is bound, else `ADAPTER_MISMATCH`; the typical QtTexture-only patch thus follows Stride's adapter, a patch with a Qt window keeps its device.
- **Threading (2026-11-14):** first step on the main thread, inside the pump (all render texture nodes serial, each only when its scene changed). A Qt render thread is planned alongside as a separate issue; the fences are its foundation.

- **Packaging (2026-11-14):** ImGui pattern. `VL.Qt` stays free of Stride (Linux); the node lives in a companion assembly, document and NuGet package `VL.Qt.Stride` (depends on VL.Qt and VL.Stride, Windows only), built from this repo. The native part (shared texture, fences) goes into `vlqt.dll`. A later `VL.Qt.Skia` would follow the same scheme. Rejected: Stride dependency in `VL.Qt.vl` (breaks Linux exports, every Qt patch would load Stride); a second document in the `VL.Qt` package (users would have to find and reference it themselves).
- **Format, colour space, alpha (2026-11-14):** `Format` pin, default `B8G8R8A8_UNorm_SRgb`, allowed: 8-bit RGBA/BGRA (UNorm and SRgb) and `R16G16B16A16_Float` from the first version; anything else is an error at the node. 8-bit textures are created typeless: Qt writes through a UNorm view (gamma-space values as in a Qt window), Stride gets the SRgb view and samples linear values (trick of `SkiaTexture`). Output is always premultiplied alpha, no pin (Qt renders premultiplied, Stride's `AlphaBlend` and `SkiaTexture` expect it); clear alpha 0 gives transparent black. Straight alpha: an unpremultiply TextureFX downstream, mentioned in the help patch. Verified (task 1.8, SmokeTest `qttexture`): elements with straight alpha come out premultiplied (50 % blue gives 0,0,128,128), but Qt does not premultiply a semi-transparent clear colour: (1, 0, 0, 0.5) is written as (255, 0, 0, 128), no valid premultiplied value. The `Clear Color` pin therefore multiplies RGB by alpha before the colour reaches QtNative.
- **Ownership and lifetime (2026-11-14):** the Stride side creates the shared texture (`Texture.New`, shared NT handle) and the node owns it; QtNative opens it, closes the NT handle right after opening and owns its wrapper, render target, offscreen scene and the two shared fences (Qt write complete, Stride read complete). The output is the same `Texture` instance until size or format change; consumers never dispose it. On a change, device loss or Dispose: free at once like `SkiaTexture` (D3D11 keeps resources the GPU still uses alive), order Qt side → fences → Stride texture, on the main thread. Size clamped to 1×1 … device limit; invalid input gives an error at the node and `null`. One texture plus two fences, no double buffer (it would change the output instance every frame; belongs to the render thread issue). No re-render when the scene did not change. Rejected: deferred disposal by one frame (unusual in vvvv, D3D11 already covers GPU use). Details decided in task 3.3: the size is clamped to the largest Texture2D of the feature level (2048 below 9_3, 4096 below 10_0, 8192 below 11_0, else 16384); `Enabled` false creates, recreates and rebinds nothing and renders nothing, `Output` keeps the last content (null if the node never rendered); Stride resets its device in place (the same `GraphicsDevice`, a new native device, its textures destroyed; `SkiaTexture`'s `OnDeviceLost` comes from the Skia render context, not from Stride), so the renderer forwards `IGraphicsDeviceService.DeviceResetting`/`DeviceDisposing` to the nodes, which unbind the Qt side, dispose their texture at once and create a new one in the next `Update`; when QtNative unbinds a scene after its own device loss the Stride texture stays valid and the node only binds again (with a new NT handle) in the next `Update`, every frame while QtNative still rebuilds (`DEVICE_LOST`), after another failed bind (adapter, open, fences) only every 60th `Update`.
- **Leak test (2026-11-14):** acceptance criterion is a SmokeTest without vvvv, with a second D3D11 device standing in for Stride: 1000× create/dispose, size and format changes, device loss on both sides; afterwards no live D3D objects (debug layer `ReportLiveDeviceObjects`) and no open handles. No manual long-run test for now.
- **Frame timing (2026-11-14):** like `SkiaTexture.DefaultRenderer`. In `Update` the node applies its scene through the reconciler and schedules itself for this frame; one renderer per app host renders all scheduled nodes at the start of Stride's draw (after all updates, before any other game system draws) in one native call: per changed scene polish, sync, render into the texture, signal the write fence. Stride waits GPU-side on that fence: same frame, no CPU wait. Time advance and event handling for these scenes must run before that draw start (detail for the plan). A node whose output nobody draws costs nothing. The hook is a `GameSystem` with `DrawOrder = int.MinValue` in `game.GameSystems` (task 3.3): `VLGame.Draw` raises the internal `DrawStarted` right before `base.Draw` runs `GameSystems.Draw`, which draws by `DrawOrder`, so the lowest order is the same moment through public API only (no reflection; a direct `GameSystems.Draw` such as the screenshot generator finds nothing scheduled and does nothing). Rejected: rendering in the Qt pump at `GetFrameFinished` (may run after Stride's draw: one frame late).
- **Name and pins (2026-11-14):** node `QtTexture` (like `SkiaTexture`), category `Qt`, from the document `VL.Qt.Stride`. Inputs: `Input` (Element), `Size` (Int2, pixels, default 1920×1080), `Space` (default DIPTopLeft, like the Renderer), `Clear Color` (RGBA/`Color4` like the Renderer, default transparent `#00000000`), `Format`, `Enabled`, `Debug` (optional). Outputs: `Output` (Texture), `Error`, `Perf` (optional). 1 DIP = 1 pixel. Rejected: `Scale` pin (not needed).
- **Separate issues (2026-11-14):** a `Clear` (bool) pin for `Renderer` and `QtTexture` together (off keeps the previous content: trails and feedback effects; needs a render target that preserves its contents, harder for the window swap chain); MSAA for windows and texture together, later.
- **Input (2026-11-14):** v1 has no input; the help patch notes say that Interaction nodes in a `QtTexture` scene are inert. Separate issue "Input for QtTexture": an optional pin takes input in texture pixel coordinates (vvvv notifications for mouse, touch, keyboard or a small own type), QtNative sends it as Qt events into the offscreen scene; the patch maps screen to texture coordinates (e.g. raycast to UV), shown in a help patch; keyboard focus for TextInput to be solved there.
- **Stride layer (2026-11-14):** `QtRenderer [Stride]` (layer, like `SkiaRenderer [Stride]`) is not part of v1: `QtTexture` plus a Stride texture drawing node covers it. Separate issue, built on `QtTexture`; it pays off with input (the layer maps the Stride window's input into the texture).
- **Native side owns the D3D work (2026-11-14, plan):** C# hands QtNative Stride's `ID3D11Device*`, immediate context and the texture's NT handle; QtNative opens the texture, creates and opens the fences and issues `Signal`/`Wait` on both contexts. All unsafe D3D11 code stays in C++ and the SmokeTest can drive it with a second device standing in for Stride. The leak test checks reference counts of both devices and the process handle count; the debug layer (`ReportLiveDeviceObjects`) in addition where it is installed.

## Package layout (2026-11-14, task 2.1)
- **How vvvv finds source packages:** `--package-repositories <dir>` treats every subfolder `<dir>\<PackageId>\` that holds `<PackageId>.vl` as a package. VL.StandardLibs is such a repository: one top-level folder per package (`VL.ImGui.Stride\VL.ImGui.Stride.vl`, `lib\`, `help\`, `src\*.csproj` building into `..\lib`). Today `tools/start-vvvv.ps1` and the F5 profiles pass `%LOCALAPPDATA%\VL.Qt-dev\<repo key>`, which holds one junction `VL.Qt` → repo root.
- **Decided:** VL.Qt stays at the repo root (no move: every path, script and the CI rely on it). The second package gets the top-level folder `VL.Qt.Stride/` as its package folder: `VL.Qt.Stride.vl`, `help/`, and the build output `lib/net10.0-windows7.0/` (ignored by git). The C# source lives in `src/VL.Qt.Stride/` like the other projects. The dev package repository gets a second junction `VL.Qt.Stride` → `<repo>\VL.Qt.Stride`. Rejected: moving VL.Qt into a `VL.Qt/` folder (StandardLibs layout; large churn for no gain), the `.vl` inside `src/VL.Qt.Stride/` (mixes package and source, `bin`/`obj` would land in the package folder).
- **Target framework:** `net10.0-windows` (VL.Stride only supports `net10.0-windows7.0`); the output folder is `lib/net10.0-windows7.0/` in repo and package alike, because `dotnet pack` rejects a TFM folder without platform version (NU1012) and the `.vl` references the same relative path in both.
- **NuGet:** `VL.Qt.Stride.nupkg` contains `VL.Qt.Stride.vl`, `lib/net10.0-windows7.0/VL.Qt.Stride.dll`, `help/`; its only dependency is `VL.Qt` at the same version (from the project reference, so both must be packed with the same `-p:Version`). VL.Stride and VL.Core are compile-time only (`ExcludeAssets="runtime"`, `PrivateAssets="all"`): they ship with vvvv. VL.Qt.dll is neither copied nor packed.

## Rejected
- CPU readback as the main path (requirement: data stays on the GPU).
