# Render Texture: Qt Scene into a Stride Texture2D

Status: phases 1-3 implemented (QtNative offscreen scene #123, package `VL.Qt.Stride` #122, `QtTexture` node #125); input #119 implemented except the SmokeTest (task 6); Stride layer `QtRenderer` #120 implemented and checked in vvvv (section "Stride layer"); phase 4 help patch and docs #127; phase 5 Qt render thread implemented (section "Qt render thread", PR #132; default: one render thread). Decided in the brainstorm of 2026-11-14. Work: #116 QtTexture, #117 Clear pin, #118 MSAA, #119 QtTexture interaction, #120 QtRenderer [Stride]. Decision log for the node that renders a Qt scene offscreen and outputs a Stride `Texture`. Reference implementation: `SkiaTexture` in VL.Stride (`VL.Stride.Runtime/src/SkiaTexture*.cs`).

## Requirements (set by the user, 2026-11-14)
- Used like `Renderer [Qt]`, but opens no window; outputs a Stride `Texture` (Texture2D).
- Several such nodes in one patch must not block each other.
- Must not block Stride rendering; runs alongside it as smoothly as possible.
- Data stays on the GPU, no CPU readback (a second node or a pin may offer a readback path).
- Ownership and disposal thought through; no leaks.
- Transparency: a `Clear Color` pin like the Renderer; clear alpha 0 gives a transparent texture.
- Resolution as an `Int2` pin.

## Facts found (2026-11-14)
- VL.Qt references only `Stride.Core.Mathematics` (runtime excluded), not Stride.Graphics/VL.Stride, and runs on Linux.
- QtNative creates its own D3D11 device per process (`device.h`), shared by all Qt windows and image uploads; Qt runs the `basic` render loop on the main thread, pumped once per vvvv frame.
- `device-sharing.md` describes the QtNative device model; before this work it named Mode 1 (Qt on Stride's device) as the design, which the code never followed.
- Bridges in other vvvv libraries (VL.StandardLibs): `SkiaRenderer [Stride]` and `SkiaTexture` live in VL.Stride.Runtime, not in VL.Skia; `VideoSourceToTexture` in VL.Stride.Runtime, `VideoSourceToSKImage` in VL.Skia, VL.Video stays renderer-free; VL.ImGui is split into the documents/packages `VL.ImGui`, `VL.ImGui.Skia` and `VL.ImGui.Stride`.
- `SkiaTexture` has two renderers: `DefaultRenderer` (Stride's device, state swap) and `DedicatedRenderer` (own device, shared texture, shared `ID3D11Fence`s for write/read completion, GPU-side wait).

## Decided
- **Device (2026-11-14):** Qt keeps the QtNative device and renders into a texture shared with Stride's device; shared `ID3D11Fence`s order Qt's write and Stride's read on the GPU (like `SkiaTexture.DedicatedRenderer`). No CPU wait, Stride's context is never touched, Qt windows and uploaded images keep working. Rendering on Stride's device (Mode 1 of `device-sharing.md`) is rejected for now: Stride would own the device and the device-lost handling of QtNative would have to be rebuilt.
- **Same adapter (2026-11-14):** QtNative's device must sit on Stride's adapter (shared handles do not cross adapters); `vlqt_offscreen_bind` compares the adapter LUIDs. If they differ, log a warning and show the error at the node, never crash.
- **Adapter move (2026-11-14, task 1.5):** moving QtNative's device to Stride's adapter with `device::rebuild` works only while no on-screen window renders on it: Qt replaces a window's QRhi only after it noticed a device loss, so a window on a healthy device would keep the old device (and images of the new one would no longer draw in it). So bind moves the device (`device::moveTo`, like a loss: images upload again) while no window has a QRhi on it and no other scene is bound, else `ADAPTER_MISMATCH`; the typical QtTexture-only patch thus follows Stride's adapter, a patch with a Qt window keeps its device.
- **Threading (2026-11-14):** first step on the main thread, inside the pump (all render texture nodes serial, each only when its scene changed). The Qt render thread (phase 5) runs the render off the main thread, on the fences. Design, measurements and state: section "Qt render thread".

- **Packaging (2026-11-14):** ImGui pattern. `VL.Qt` stays free of Stride (Linux); the node lives in a companion assembly, document and NuGet package `VL.Qt.Stride` (depends on VL.Qt and VL.Stride, Windows only), built from this repo. The native part (shared texture, fences) goes into `vlqt.dll`. A later `VL.Qt.Skia` would follow the same scheme. Rejected: Stride dependency in `VL.Qt.vl` (breaks Linux exports, every Qt patch would load Stride); a second document in the `VL.Qt` package (users would have to find and reference it themselves).
- **Format, colour space, alpha (2026-11-14):** `Format` pin, default `B8G8R8A8_UNorm_SRgb`, allowed: 8-bit RGBA/BGRA (UNorm and SRgb) and `R16G16B16A16_Float` from the first version; anything else is an error at the node. 8-bit SRgb textures are created typeless, Stride gets the SRgb view. UNorm textures hold what Qt renders, gamma-space values as in a Qt window. SRgb and Float textures hold linear values (2026-11-15): Qt renders premultiplied gamma-space values, and sRGB decoding does not commute with premultiplication, so Qt's values read through an SRgb view made every pixel with 0 < alpha < 1 too dark (50 % red over the Stride background gave a red of 132 instead of about 188), and a Float texture read gamma values as linear (all colours too dark). So for these formats Qt renders into an `R16G16B16A16_Float` texture of QtNative, and after each frame a fullscreen pass (`offscreen/linear_pass.cpp`) writes a × linear(c) into the shared texture: unpremultiply, sRGB decode, premultiply, written through the SRgb view (the GPU encodes) or as float. Opaque pixels read as before; half-transparent colours still differ from a Qt window, because Stride blends in linear light and a Qt window in gamma space. The bind format is the format Stride samples (`vlqt_offscreen_bind`). Output is always premultiplied alpha, no pin (Qt renders premultiplied, Stride's premultiplied blend state, `AlphaBlendPremultiplied` in vvvv, and `SkiaTexture` expect it; vvvv's `AlphaBlend` is for straight alpha); clear alpha 0 gives transparent black. Straight alpha: an unpremultiply TextureFX downstream, mentioned in the help patch. Verified (task 1.8, SmokeTest `qttexture`): elements with straight alpha come out premultiplied (50 % blue gives 0,0,128,128), but Qt does not premultiply a semi-transparent clear colour: (1, 0, 0, 0.5) is written as (255, 0, 0, 128), no valid premultiplied value. The `Clear Color` pin therefore multiplies RGB by alpha before the colour reaches QtNative.
- **Ownership and lifetime (2026-11-14):** the Stride side creates the shared texture (`Texture.New`, shared NT handle) and the node owns it; QtNative opens it, closes the NT handle right after opening and owns its wrapper, render target, offscreen scene and the two shared fences (Qt write complete, Stride read complete). The output is the same `Texture` instance until size or format change; consumers never dispose it. On a change, device loss or Dispose: free at once like `SkiaTexture` (D3D11 keeps resources the GPU still uses alive), order Qt side → fences → Stride texture, on the main thread. Size clamped to 1×1 … device limit; invalid input gives an error at the node and `null`. One texture plus two fences, no double buffer (it would change the output instance every frame; belongs to the render thread issue). No re-render when the scene did not change. Rejected: deferred disposal by one frame (unusual in vvvv, D3D11 already covers GPU use). Details decided in task 3.3: the size is clamped to the largest Texture2D of the feature level (2048 below 9_3, 4096 below 10_0, 8192 below 11_0, else 16384); `Enabled` false creates, recreates and rebinds nothing and renders nothing, `Output` keeps the last content (null if the node never rendered); Stride resets its device in place (the same `GraphicsDevice`, a new native device, its textures destroyed; `SkiaTexture`'s `OnDeviceLost` comes from the Skia render context, not from Stride), so the renderer forwards `IGraphicsDeviceService.DeviceResetting`/`DeviceDisposing` to the nodes, which unbind the Qt side, dispose their texture at once and create a new one in the next `Update`; when QtNative unbinds a scene after its own device loss the Stride texture stays valid and the node only binds again (with a new NT handle) in the next `Update`, every frame while QtNative still rebuilds (`DEVICE_LOST`), after another failed bind (adapter, open, fences) only every 60th `Update`.
- **Leak test (2026-11-14):** acceptance criterion is a SmokeTest without vvvv, with a second D3D11 device standing in for Stride: 1000× create/dispose, size and format changes, device loss on both sides; afterwards no live D3D objects (debug layer `ReportLiveDeviceObjects`) and no open handles. No manual long-run test for now.
- **Frame timing (2026-11-14):** like `SkiaTexture.DefaultRenderer`. In `Update` the node applies its scene through the reconciler and schedules itself for this frame; one renderer per app host renders all scheduled nodes at the start of Stride's draw (after all updates, before any other game system draws) in one native call: per changed scene polish, sync, render into the texture, signal the write fence. Stride waits GPU-side on that fence: same frame, no CPU wait. Time advance and event handling for these scenes must run before that draw start (detail for the plan). A node whose output nobody draws costs nothing. The hook is a `GameSystem` with `DrawOrder = int.MinValue` in `game.GameSystems` (task 3.3): `VLGame.Draw` raises the internal `DrawStarted` right before `base.Draw` runs `GameSystems.Draw`, which draws by `DrawOrder`, so the lowest order is the same moment through public API only (no reflection; a direct `GameSystems.Draw` such as the screenshot generator finds nothing scheduled and does nothing). Rejected: rendering in the Qt pump at `GetFrameFinished` (may run after Stride's draw: one frame late).
- **Name and pins (2026-11-14):** node `QtTexture` (like `SkiaTexture`), category `Stride.Textures.Source` (as `SkiaTexture`; `Qt` until 0.10.0), from the document `VL.Qt.Stride`. Inputs: `Input` (Element), `Size` (Int2, pixels, default 1920×1080), `Space` (default `DIPTopLeft`, like the Renderer; the device pixel ratio is 1, so `PixelTopLeft` equals `DIPTopLeft`), `Clear Color` (RGBA/`Color4` like the Renderer, default transparent `#00000000`), `Format`, `Enabled`, `Debug` (optional). Outputs: `Output` (Texture), `Error`, `Perf` (optional). 1 DIP = 1 pixel. Rejected: `Scale` pin (not needed).
- **Separate issues (2026-11-14):** a `Clear` (bool) pin for `Renderer` and `QtTexture` together (off keeps the previous content: trails and feedback effects; needs a render target that preserves its contents, harder for the window swap chain); MSAA for windows and texture together, later.
- **Input (2026-11-14, designed 2026-11-15 in #119 task 1):** v1 had no input (Interaction nodes in a `QtTexture` scene were inert). #119 adds it; the contract is at the end of this file.
  - *Pin type:* an optional pin `Input Notifications` of type `IObservable<INotification>` (`VL.Lib.IO.Notifications`, VL.Core) on `QtTexture`. That is what vvvv's input sources give (`InputManager.GetNotifications(inputSource)` in VL.Stride, `SkiaControl.Notifications`); mouse, touch, keyboard and focus come in one stream, and the patch can merge, filter and transform it with the reactive nodes. Rejected: an own pointer struct (users would build it from notifications themselves, keyboard would need a second type).
  - *Coordinates:* positions in the notifications are texture pixels, top-left origin, 1 DIP = 1 pixel (as the scene). `ClientArea` is ignored. Positions outside 0 … Size are valid and forwarded (hover ends, a drag goes on, a press there takes the focus).
  - *Helper node:* one, `ToTexturePixels` in `VL.Qt.Stride`: notifications of a window → texture pixels for a texture on Stride's unit quad (-0.5 … 0.5 in its local XY plane, +Y up), placed by `World` and seen through `View` and `Projection`; per notification a ray from `Position`/`ClientArea` through the inverse of World·View·Projection, cut with the plane z = 0, u = x + 0.5, v = 0.5 − y, times `Texture Size`. Fullscreen is `World` = Scaling (2, 2, 1) with identity View and Projection; a zero matrix counts as identity (an unconnected Matrix pin). Covers fullscreen, a quad in 3D and (approximately) any flat placement; a texture on an arbitrary mesh needs the patch's own raycast to UV and then feeds pixel positions directly. Rejected: a 2D `Matrix` variant (the quad node covers it), a UV-function delegate pin (not patch-friendly).
  - *Translation (C#, in VL.Qt so a later `VL.Qt.Skia` reuses it):* `OffscreenInput.Notify` maps mouse down/up/move/wheel/horizontal wheel/lost, touch down/move/up and key down/up/press to the native calls: WinForms `MouseButtons` and `Keys` to Qt's `MouseButtons`, `KeyboardModifiers` and `Qt::Key`; `KeyPress` gives its character as text (`send_text`); `LostFocusNotification` gives `set_focus(0)`. vvvv has no pen notification: pen arrives as touch or mouse from Windows, and the native side delivers a pen as a window on Windows gets one, for a host that sends it. Horizontal wheel: no vvvv input source creates `MouseHorizontalWheelNotification`, so its sign is set here: positive `WheelDelta` = left, as Qt's `angleDelta().x()` and VL.ImGui (the only consumer), passed through unchanged (decided 2026-11-15). `MouseClickNotification` is ignored (Qt derives clicks and double clicks itself).
  - *Native injection (as implemented, #119 tasks 2 and 3):* QtNative sends `QMouseEvent`, `QWheelEvent`, `QTouchEvent` and `QKeyEvent` with plain `QCoreApplication::sendEvent` to the scene's `QQuickWindow`: synchronous and not marked spontaneous (like `vlqt_test_send_*`; the spontaneous flag is not needed), so handlers, `scene/handlers.cpp`, `vlqt_scene_poll`, `EventReader`, `FeedbackRouter` and channels work unchanged. Each scene has its own mouse, touchscreen and pen `QPointingDevice` (point ids and grabs live in the device: a press sent to two scenes does not cancel the other's grab); the touchscreen device sends all active points per event as `vlqt_test_send_touch` does (its state machine is shared, plus `CANCEL` for every point of a device), the pen is a stylus (pointer type Pen, so `Devices = Pen` of the Interaction nodes matches) that sends `QTabletEvent`s and, when nobody accepts one, the same as a mouse event from the stylus synthesized like `QGuiApplication` does for Qt's Windows plugin (WM_POINTER); pen `id` is ignored (one point), `CANCEL` drops the pen's grabs without a release, `LEAVE` ends its hover as for the mouse. A mouse event gets `buttons` = the buttons held after the event; press or release without a changed button is `BAD_ARGUMENT`, and so is `LEAVE` on touch. `MouseButtonDblClick` is synthesized natively from two presses, as `QGuiApplication` does. Text goes as a `QKeyEvent` press/release with the text and `Qt::Key_unknown` (the path of `vlqt_test_send_key_text`); a `QInputMethodEvent` commit is the fallback if an item ignores it. Key events reach the focus item only: `QShortcut` does not see them.
  - *Keyboard focus (as implemented, #119 task 3):* an offscreen `QQuickWindow` never becomes `QGuiApplication::focusWindow()`. QtNative gives the scene focus by sending `QFocusEvent` `FocusIn` to its window, so `activeFocusOnPress` of TextInput and the active focus item work; `FocusOut` takes it. Deviation from the first design: Qt Quick gives the root item focus only while the app's focus window is the window, its render window or none, and a scene has no render window. QtNative therefore uses a render control with private API, `SceneRenderControlPrivate` (derived from `QQuickRenderControlPrivate`, `isRenderWindow` also true for the current focus window while the scene is focused; the pattern of `QQuickWidget`). This needs `qquickrendercontrol_p.h` and `qquickwindow_p.h` and must be checked on every Qt update. `FocusOut` alone keeps the active focus item when no window has focus, so a focus loss first releases it with `releaseFocus` (shared with the `FocusRelease` filter). Rule, like a window: a press (mouse, touch) inside 0 … Size focuses the scene before the press is delivered, a press outside or `set_focus(0)` (the host window lost focus) unfocuses it; key and text events of an unfocused scene are dropped (result OK). The `FocusRelease` filter of windows (#374: Esc reverts and releases, a press outside the focused element releases) is installed on scenes too. Several `QtTexture`s fed by one window: only the last one pressed has focus. Rejected: `QQuickRenderControl::renderWindow` (needs a real `QWindow` of the host; vvvv's Stride window is not a Qt window).
  - *Timing:* the node subscribes to the pin, queues notifications (lock, reused list; they may arrive off the main thread) and drains them at the start of `Update`, before `OffscreenScene.Update`: the events act on the items of the previous apply, the render in `DrawStarted` of the same frame shows the result, the events of the scene (`PollEvents` after the batch) reach the element nodes and channels in the next frame, as with windows. `Enabled` false drains and drops the queue (a frozen scene takes no input). A new observable instance on the pin re-subscribes; Dispose unsubscribes.
- **Stride layer (2026-11-14):** `QtRenderer [Stride]` (layer, like `SkiaRenderer [Stride]`) is not part of the first `QtTexture` version; #120, built on `QtTexture`. Design: section "Stride layer".
- **Native side owns the D3D work (2026-11-14, plan):** C# hands QtNative Stride's `ID3D11Device*`, immediate context and the texture's NT handle; QtNative opens the texture, creates and opens the fences and issues `Signal`/`Wait` on both contexts. All unsafe D3D11 code stays in C++ and the SmokeTest can drive it with a second device standing in for Stride. The leak test checks reference counts of both devices and the process handle count; the debug layer (`ReportLiveDeviceObjects`) in addition where it is installed.

## Stride layer (#120, designed 2026-11-15)

Goal set by the user: half-transparent Qt content drawn over a Stride scene looks (almost) the same as in a Qt window. `QtTexture` stays the node for textures that the patch manipulates further; it blends in linear light. `QtRenderer` looks like a Qt window but outputs no texture. Checked in vvvv on 2026-11-15 (win-arm64, help patch `HowTo Draw Qt in a Stride Scene`): the layer in the Stride window and the same elements in a Qt window look the same, half-transparent overlap included; Button and Slider react to the window's input; `Error` stays empty. Screenshot: `docs/images/qtrenderer-vs-qt-window.png`.

- **Why not blending the texture through Stride's view:** Stride blends through an SRgb view in linear light, a Qt window blends in gamma space. No change of the texture alone (TextureFX, a pass) can make up for it: Stride's result X + (1 − α)·linear(bg) is linear in the background, the Qt window's linear(c + (1 − a)·bg) is not. Computed over 20 000 random cases, the best per-pixel approximation is off by 7/255 on average and 25/255 at p95. Example, 50 % red over (30, 148, 102): Qt window (142, 74, 51), Stride linear (189, 107, 73), the SRgb texture with gamma values before 2026-11-15 (129, 107, 73).
- **How Skia does it:** `SkiaRenderer [Stride]` looks like a Skia window because it draws straight into the back buffer, whose resource is not sRGB (flip model; only Stride's view is SRgb): Skia blends on the raw bytes, in gamma space (`GetResourceFormat` in `SkiaRenderer.cs`). `SkiaTexture` has the same difference as `QtTexture`.
- **Composition (decided):** the layer renders into an internal `QtTexture` core with a **UNorm** format (gamma-space values, premultiplied, as a Qt window). In its draw it binds a **UNorm render target view on the resource of the current target** and draws a fullscreen quad into the viewport with premultiplied blending (One, InvSrcAlpha): exactly the arithmetic of a Qt window, one draw, no readback. The UNorm view comes from Stride's `Texture.ToTextureView` (no SharpDX); if the target's own view is UNorm it is used as it is. The blend state is Stride's `BlendStates.AlphaBlend`, which is premultiplied (vvvv calls it `AlphaBlendPremultiplied`). The quad is drawn with point sampling (the texture has the size of the viewport, so texels map 1:1) and without a depth buffer (neither tested nor written). Condition: the target's resource is 8-bit RGBA/BGRA and allows a UNorm view, i.e. its resource format is UNorm or typeless (window back buffer, typeless render texture). So the layer belongs after the 3D scene (as `SkiaRenderer` in a Stride window), not inside it with an HDR float target.
- **Fallback (decided):** any other target (resource `*_UNorm_SRgb` not typeless, float, MSAA without a UNorm view) gets the texture in the target's view format with `QtTexture`'s linear premultiplied values and premultiplied blending (as `AlphaBlendPremultiplied`): correct for opaque content, half-transparent colours as with `QtTexture`. A view format that `QtTexture` does not support gets `B8G8R8A8_UNorm_SRgb` if it is an SRgb format, else `R16G16B16A16_Float` (same linear values). The layer logs this once per target change and shows it as a hint at its `Error` output.
- **Shared core:** the texture, bind/rebind, lifetime, device loss and scheduling of `QtTextureNode` move into one internal class in `VL.Qt.Stride`; `QtTextureNode` and `QtRendererNode` use it; `QtTextureRenderer` schedules the core, not the node.
- **Timing:** as issue #120 proposes: the layer schedules its core in `Update` with the viewport size of its last draw (a resize shows one frame later), the batch renders in `DrawStarted`, the draw composes the same frame's content. Before the first draw there is no size and nothing renders. The layer draws the texture only in the format chosen for the current target: after a target change to another format it draws nothing for one frame, until the next `Update` has recreated the texture (while `Enabled` is false that `Update` does not recreate it, so the layer stays empty until re-enabled). `Enabled` false freezes like `QtTexture` (no apply, no render, no input) and the layer keeps drawing the last content.
- **Input:** like `SkiaRenderer.InputHandling.cs`: the render context's window input source (`GetWindowInputSource`), `InputManager.GetNotifications`, positions minus the viewport origin give texture pixels (1 DIP = 1 pixel as in `QtTexture`), then the input path of #119. A new input source re-subscribes.
- **Name and pins:** node `QtRenderer`, class `QtRendererNode : RendererBase` in `VL.Qt.Stride`, category `Stride.Rendering` like `SkiaRenderer`. Inputs `Input` (Element), `Space` (default `DIPTopLeft`, see `QtTexture`), `Clear Color` (default transparent), `Enabled`, `Debug` (optional); outputs `Output` (`IGraphicsRendererBase`, the layer) and `Error`. Size comes from the viewport, format from the target.

## Qt render thread (spike 2026-11-15, task 5.1; implemented in 5.2a)
**Implemented** (5.2a, `render_thread.h/.cpp`, `offscreen/`, `device.cpp`): a pool of Qt render threads shared by every scene of the process, default 1; a scene gets its thread at `vlqt_offscreen_create`, round robin, and keeps it (no per-scene mode, no thread per scene). The pool size comes from the environment variable `VLQT_OFFSCREEN_THREAD` (`0` main thread, `n` = 1 … 16 threads, unset = 1) or from the export `vlqt_offscreen_set_render_threads(n)`, which wins; the variable is read at the first scene, which logs the mode (Info, category `vlqt.offscreen`). `set_render_threads` may be called at any time (E7): it applies to the scenes created afterwards, a scene keeps its thread, and the pool only grows. Pool threads are created at first use and live until the process ends. There is no C# switch: the environment variable is the diagnosis switch (`docs/diagnostics.md`). The spike measured below (branch `spike/116-render-thread`, SmokeTest `qttextureperf`) also had a thread per scene; that variant is dropped.

**Measured** (2026-11-15; Snapdragon X Plus 8 cores, Adreno X1-45, 16 GB, Windows 11 ARM64, Qt 6.12.0; `dotnet run --project src/VL.Qt.SmokeTest -c Release -- --only qttextureperf`, two rounds, round 2 below, round 1 within ±10 % except the noisy first runs). Scene: 1280×720, 2000 rounded rectangles + 80 texts ("heavy") or 100 + 4 ("light"); per frame 50 colours, 10 texts and a frame-number marker change. A frame imitates vvvv: apply, `render_batch`, 6 ms Stride CPU work, then a GPU read of scene 0's texture on the test device (Map; stands in for Stride's draw). Medians in ms:

| 4 heavy | 2.63 / 0.18 / 0.17 / 0.20 | 18.3 / 11.8 / 9.7 / 8.9 | 2.5 / 2.4 / 3.4 / 4.8 | 1.0 / 4.5 / 2.3 / 1.4 |

- Main-thread time per QtTexture drops from 0.7–2.8 ms to 0.07–0.34 ms (polish + blocking sync + hand-off; sync alone 0.06–0.19 ms). Every frame of every run held its own marker (0 of 230 misses): same frame.
- More threads shorten the frame only for several heavy scenes, and pay with CPU: render time per scene grows 1.4× (pool 2) to 3× (per scene) through contention (cores shared with vvvv, Qt-global locks, the context lock: 0.12–0.16 ms wait per scene frame per scene vs < 0.001 ms with one thread). Round 1 of the first matrix showed ±50 % run-to-run noise on this laptop for the 4- and 8-scene cases; the trend held.
- `VLQT_OFFSCREEN_FOREIGN_FLUSH=1` (flush Stride's context after its read signal) changed nothing measurable here (the test's Map flushes anyway); in vvvv Stride flushes only at Present, so without it Qt's GPU work could not start before Stride's first flush.
- The `qttexture` suite (bind/unbind, formats, batch, alpha, adapter move, device loss of QtNative's device via D3D11On12, foreign release, 1000× leak test, window comparison) passes with one render thread: 208 PASS, 0 FAIL.
- WARP: the foreign context waiting for a value the render thread signals later deadlocks (9 of 10 runs; hardware: never). QtNative falls back for a binding with a software device: the main thread waits until the render thread has submitted the signal, then queues the wait (no gain, correct; 2 of 2 runs).

**Decided** (answers to 5.1):
- **(a) Device model:** keep QtNative's one shared D3D11 device. The render thread uses its immediate context like the main thread; the context gets `ID3D11Multithread::SetMultithreadProtected(TRUE)` and every stateful sequence takes a recursive lock (`ID3D11Multithread::Enter/Leave`): on the render thread `Wait(read) + beginFrame` and `endFrame + Signal(write) + Flush` (QRhi D3D11 records into its own command buffer and executes it in `endFrame`; `render()` only maps dynamic buffers, which the per-call protection covers). Rejected: an own device per render thread (uploaded images and QtImageItem textures live on the shared device and would have to be opened as shared resources per scene; device loss and adapter move would exist twice); deferred contexts (QRhi D3D11 needs the immediate context: Map READ for readbacks and snapshots, timestamp queries, Flush; `QQuickGraphicsDevice::fromDeviceAndContext` takes the immediate context).
- **(b) Threads:** one render thread for all QtTextures of the process (scenes of every app host), as a pool whose size is a QtNative setting with default 1. Rejected: one thread per node (3× CPU per scene, contention grows with the node count). A pool of 2 is the measured option for patches with several heavy scenes; scenes are assigned at create, round robin.
- **(c) Same frame: kept.** `render_batch` (draw start) on the main thread: per scene Signal(read) on Stride's context and polish; one blocking job per render thread: Wait(read) on Qt's context, beginFrame, sync (the items are not touched meanwhile); Wait(write, n) on Stride's context; then a posted job per thread: render, endFrame, Signal(write, n), Flush. Stride's GPU waits for a value signalled later ("wait before signal"); its CPU never waits. If Qt's render takes longer than Stride's CPU frame, Stride's GPU waits (read wait column). Back pressure: the next frame's sync job queues behind the previous renders, so at most one frame per scene is in flight and the main thread blocks only when the render thread is more than a frame behind. Flush Stride's context after the read signals (one flush per batch). Every queued Wait(write, n) must get its signal: the render job signals also when beginFrame or render fails. Software devices (WARP): wait for the submission on the main thread, then queue the wait. No one-frame-latency mode.
- **(d) Output texture:** one texture with the two fences stays (same frame needs no second texture; the output instance stays the same). Double buffering (changes the instance every frame) and a GPU copy into a stable texture (full-texture copy per frame) are needed only for a latency mode where Stride never waits; if that mode comes, the copy is preferred because consumers keep one instance.
- **(e) Thread affinity:**

| Object / call | Thread |
|---|---|
| `QQuickWindow`, items, `vlqt_scene_apply`, reconciler (`OffscreenScene`, `CommandWriter`), animation driver, `polishItems`, input events, `setGeometry` | main |
| `QQuickRenderControl::prepareThread` | main, once at create, before initialize |
| `initialize`, `beginFrame`, `sync`, `render`, `endFrame`, `invalidate`, the scene's QRhi and scene graph, `setRenderTarget` + `ensureCustomRenderTarget` in unbind | render thread (`sync` and the calls the main thread waits for: blocking job) |
| `bind` (open texture, fences: device calls are free-threaded) | main; its unbind and initialize run as blocking jobs on the render thread |
| unbind, Stride device loss, `vlqt_scene_destroy` | main, after a blocking job on the render thread (it runs after every posted render: drains): unbind there; destroy also `invalidate` + delete the QRhi there, then the main thread deletes window and render control |
| QtNative device loss (`device::Listener`) and adapter move | main; `lost` and `restored` run per scene as blocking jobs on its render thread |
| `QQuickWindow` signals (`beforeSynchronizing`: UpdateGate, PerfMonitor) | render thread; sync ones while the main thread waits, `before/afterRendering` concurrently: PerfMonitor needs atomics or per-thread values |
| Stride's immediate context (Signal/Wait) | main only (Stride draws there) |

- **Input (#119):** events go to the offscreen `QQuickWindow` on the main thread, as now: the items live there, and Qt's frame-synchronous delivery (hover re-check) runs in `polishItems`, also main thread. #119 must: deliver synchronously (`QCoreApplication::sendEvent` or `QWindowSystemInterface` with synchronous delivery) in the node's Update or at the latest before `render_batch`, not through the pump at `GetFrameFinished` (after the draw: one frame late); never call into the scene from the render thread or from a Qt render signal; use item geometry, never the scene graph or QRhi, for mapping and hit tests; take the scene size from the binding set on the main thread (bind drains the render thread). Then events need no lock: the render thread touches items only during sync, while the main thread waits.

**Open risks:** the shared-thread and pool numbers come from one laptop, measure once on an x64 desktop GPU. Verified in 5.4 and no longer open: a queued Wait(write, n) does not hang when QtNative's device is removed (the frame is discarded or completes, slowest foreign readback 3 ms); the main-thread users of QtNative's context take the lock (window frames, upload QRhi frames, staging copies); snapshots (`QQuickItemGrabResult`) of a threaded scene under load (`qttextureperf`, 1–8 heavy scenes, both modes: every snapshot after 1 frame, same frame kept, main-thread time unchanged).

**Implementation (PR #132):** QtNative `render_thread.*` (pool threads `vlqt-render-N`), `offscreen.*` (threaded batch, WARP fallback), `device.*` (`ContextLock`, window frame locks released after the pump, before rebuild and before every blocking render-thread job); switch `VLQT_OFFSCREEN_THREAD` / `vlqt_offscreen_set_render_threads` (`docs/diagnostics.md`); tests: SmokeTest `qttexture` in both modes in `tools/build.ps1 -Test` (leak test and device loss threaded, never-signalled, WARP, window + scene through a device loss), `qttextureperf` with limits (`docs/profiling.md`).

## Clear pin (spike 2026-11-15, #117 task 1)
**Decision: feedback layer** in the scene, one implementation for windows and offscreen scenes; no target-specific paths (`PreserveColorContents` for the texture, intermediate texture for the swap chain) are needed. Implementation: `src/VL.Qt.Native/scene/previous_frame_layer.h/.cpp` (`PreviousFrameLayer`, `ClearState::setClear` in `scene/clear_state.h`), driven by the command `SET_CLEAR` (task 2/3, see "Proposed protocol" below; the spike's test export `vlqt_test_set_clear` is gone) and the SmokeTest scenario `clear-pin` (`src/VL.Qt.SmokeTest/ClearPinTest.cs`, PNGs `build/smoke/clear_pin_*.png`); task 5 completes the scenario.

- *Structure:* while Clear is off, a `QQuickShaderEffectSource` (recursive, live, `hideSource`, `NoMirroring`) of the scene root sits under the content item, sized to the root; the root is drawn only into it. Its texture is drawn by a view item (`QSGSimpleTextureNode`) as the bottom child of the root (z -1e9, untracked: REPARENT does not count it). Per frame the source renders the root (view = previous frame, then the elements over it) into its second texture and swaps; the window draws the source over the clear colour. Debug and perf overlays and snapshot frame sources stay outside the root: never accumulated.
- *First frame:* the view draws nothing while the previous texture is undefined (no texture yet, new item size, new texture size at the same item size). The texture starts transparent, and premultiplied "over" makes "transparent texture over the clear colour" equal to "clear colour in the texture", so the first frame after switching off and after a resize starts from the clear colour. Verified: window and offscreen, no garbage pixels.
- *Fade with the alpha of Clear Color (#138):* with Clear off and alpha > 0 the view draws a full-size fill with the clear colour over the previous frame (a `QSGRectangleNode` after its texture node, premultiplied "over": `out = C·a + prev·(1 − a)`), so trails fade toward the clear colour; alpha 0 draws no fill (accumulation as before), alpha 1 gives the result of Clear on. `ClearState::setColor` hands the colour to the layer (`PreviousFrameLayer::setFill`) at runtime, the layer stays. Frame clear: Qt clears the window with the colour as given (`QQuickWindow::setColor` stores it straight, the renderer passes it to `beginPass`), and the window draws the layer texture over it, so where the texture is not opaque yet (first frames after switching off or a resize, the fill only raises its alpha toward 1) the clear colour shows through a second time: the colour comes out right only because Qt clears with straight RGB, the alpha is counted twice (`a + a·(1 − a)` in the first frame). Decided: for 0 < alpha < 1 with a layer, `ClearState::applyColor` clears the window to the clear colour made opaque; "texture over opaque C" is exactly the result of Clear on with an opaque C (also under semi-transparent elements) and needs no assumption about Qt's handling of a frame-clear alpha. Consequence: with Clear off and 0 < alpha < 1 the output is opaque from the first frame (a `QtTexture` too; the fill makes it opaque within a few frames anyway, "Limits" in #138). Rejected: clearing the window to transparent and letting the fill do all the work (the first frames would start from `C·a`, a dark fade-in in a window). Alpha 0 and 1 keep the clear colour as it is.
- *Resize:* clears once (window resize; offscreen rebind with another size). The first prototype keyed only on the texture size and showed the old texture stretched for one frame; keying on the item size fixed it.
- *Fading:* a full-size black rectangle at 25 % alpha fades the trail and the clear colour to black in 30 frames, the element drawn last stays. RGBA8 leaves a residue (a value of 1 stays, 8-bit rounding), as in other 8-bit feedback loops.
- *Attachment:* the `ClearState` of the `vlqt::Scene` (one per window handle, window or offscreen scene) owns the layer and holds the state (`clearFrames`, `feedbackSamples`); the layer is derived from it and bound to one `QQuickWindow`: the source is a child of that window's content item, the view a child of `Scene::root`, both sized to the root (which `Scene` sizes from the window's `widthChanged`/`heightChanged`), the textures live in that window's QRhi. It never moves to another window. The window swap of #118 (sample count change) goes through `Scene::moveToWindow`, which calls `ClearState::release()` before the root leaves the old window (drops the layer, keeps the state), moves the root and sets `Scene::window`, then `ClearState::restore()` (rebuilds the layer for the new window when Clear is off). The trail is lost then and the first frame starts from the clear colour, as after a resize. Rejected: reparenting the source to the new window (its layer texture belongs to the old QRhi and is recreated anyway; the size connections point to the old window). `setClear` itself is release + restore.
- *MSAA (#118):* windows render with 4 samples (`vlqt_app_init`, `QSurfaceFormat::setSamples(4)`), offscreen scenes with 1 (their render target). Qt's layer takes the sample count of the render target when its `samples` is 0 or 1, and resolves into its sampled texture every frame; more than 1 forces that count; the real command has no samples value, the layer always takes the target's count. Measured on the edges of a rotated square (distinct values between background and fill, n samples give n − 1): window Clear on 3, layer default 3, layer 1 3, layer 2 1, layer 4 3, layer 8 7; offscreen Clear on 0, layer default 0, layer 4 3. So the default (0) keeps the edges exactly as with Clear on for both targets, and no `samples` value is set: no edge loss, and an MSAA change of #118 is followed without code here (a new window goes through release/restore, a new offscreen render target is inherited at the next grab). Forcing samples on an offscreen layer would add anti-aliasing that Clear on does not have. Cost with an MSAA window: the root renders into a 4-sample layer plus its resolve, then the window pass (one full-size quad and overlays) still renders at 4 samples and resolves the swap chain; the window's MSAA buys nothing while Clear is off, but it cannot be switched per frame (it is the swap chain's format). The numbers below include it; layer 1 and layer 4 cost the same (both are 4 samples).
- *Software backend* (Qt Quick software, Linux CI): it draws no `ShaderEffectSource`, so the layer would show a black frame. `ClearState::restore` creates no layer there: Clear off renders as Clear on, with one warning per scene ("Clear off needs a QRhi scenegraph; ignored on the Qt Quick software backend"); the SmokeTest skips the layer checks there.
- *Effect layers, Debug overlay, Snapshot:* a Blur element draws with Clear off; the debug overlay leaves no outlines after it is switched off; a snapshot of an element shows the element once (its frame source renders the element, not the root).
- *Rendering:* a recursive live layer requests the next frame itself, so while Clear is off Qt renders every pump, also without a scene change (30 of 30 idle pumps counted as changes, offscreen 10 of 10 batches rendered). This matches Skia and Stride renderers with Clear off (they render every vvvv frame, a fade keeps fading) and replaces the issue's "only when Qt renders". Clear on: no layer, no extra cost (layer created on switching off, deleted on switching on).
- *Cost* (Snapdragon X Plus, Adreno X1-45, Qt 6.12.0, swap interval 0, DPR 1.5, window 4x MSAA; GPU time per frame from the perf sample, means of 120 frames, 3 interleaved rounds, 7 runs; the GPU clock varies between runs): 800×600 DIP +0 to +0.25 ms (e.g. on 0.44 / off 0.69 ms, in other runs both 1.6–2.3 ms); 1920×1080 DIP (2880×1620 px) Clear on 2.0–2.2 ms vs off 2.3–2.5 ms in most runs, up to 3.3–3.5 ms in one, so about +0.3 ms, at worst +1 ms. CPU render 0.02 → 0.05 ms. Memory: two textures of the window size (recursive), RGBA8: 2 × 18.7 MB at 2880×1620, plus the 4-sample render buffer of the layer on a window (computed, not measured: about 75 MB at that size).

**Found on the way (fixed in the prototype, needed in task 3):**
- The root of an offscreen scene was 0 × 0 (its content item is sized only for a shown window), and a `ShaderEffectSource` draws nothing of an empty source item. Task 3: `Scene` sizes the root of every scene to the window (`QWindow` width/height, not the content item), the layer's source and view follow the root. Element positions and `EVENT_SCENE_BOUNDS` do not depend on the root's size.
- `QQuickShaderEffectSource::textureProvider()` may only be queried on the render thread: an offscreen scene renders on a thread of its own, so the view connects to the provider in `updatePaintNode`.
- The source enters the window before its source item is set: a `ShaderEffectSource` without a window takes a window reference on the root in `setSourceItem` and a second one when it enters the window, but gives back only one, so the root kept the old window and the #118 window swap crashed ("Cannot use same item on different windows").
- Resize connections need one context per item: the view is deleted at once, the source with `deleteLater`, which the pump does not run promptly; a lambda on both crashed on the next resize.

**Open risks:**
- OpenGL (Linux): `NoMirroring` and the view's texture coordinates are verified on D3D11 only; check the orientation under WSL/Linux in task 5.
- `vlqt_test_window_grab` (`grabWindow`) renders the scene once more: probably one extra accumulation step per grab (not measured). Snapshots of elements are unaffected.
- Input through the hidden root is expected to work (`hideSource` changes only drawing), not tested yet: task 5 should press and hover an element with Clear off.
- 8-bit residue of fades; a float format for the source (`RGBA16F`) would fix it at twice the memory (option, not decided).
- A user `z` below -1e9 would draw under the view (no element pin sets z today).

**Proposed protocol for task 2:** a command, not a window mode or export, because the clear colour already travels as a command and `Scene` (C#) writes it for windows and offscreen scenes alike. New opcode `VLQT_OP_SET_CLEAR = 9` in `protocol.h` (`Protocol.Op.SetClear` in `Protocol.cs`), payload `u32 clear` (1 = clear every frame, the default; 0 = keep the previous frame), handled in `Scene::apply` by `Scene::setClear(clear != 0)`; `RESET` leaves it as it is (like `CLEAR_COLOR`), `Scene` (C#) sends it again after a resync. C#: `CommandWriter.SetClear(bool)`, `Scene.Update(input, space, clearColor, clear)` writes it on change next to `ClearColor`, so `WindowScene` and `OffscreenScene` need no own path. Rejected: a bit in `vlqt_window_mode` (`vlqt_window_set_mode` returns early for offscreen scenes and `OffscreenScene` does not call it), a new export (a second path beside the command buffer, out of frame order with the apply).

## MSAA (spike 2026-11-15, #118 task 1)
**Measured on** Snapdragon X Plus, Adreno X1-45, Windows 11 ARM64, Qt 6.12.0, D3D11, display scale 150 % (spike scenario `msaaspike`, since replaced by `Msaa`, which has no cost measurement). Qt sources read: `qsgrenderloop.cpp`, `qsgrhisupport.cpp`, `qquickrendertarget.cpp`, `qsgrhilayer.cpp`, `qquickrendercontrol.cpp`, `qrhid3d11.cpp` (all v6.12.0).

**Facts**
- *Window count:* Qt gives a swap chain `max(QSurfaceFormat::defaultFormat().samples(), window->requestedFormat().samples())` (`QSGRhiSupport::chooseSampleCountForWindowWithRhi`). With today's `setSamples(4)` in the default format (`vlqt_app_init`) no window can have fewer than 4 samples: the default format must lose its samples and each window sets its own (the prototype does that, 4 per window, so today's look stays).
- *Fixed per QQuickWindow:* the basic render loop chooses the count once, when it creates the window's QRhi (`QSGGuiThreadRenderLoop::ensureRhi`, `data.sampleCount`; also the render context's count). `QWindow::destroy()` + `show()` releases and recreates the swap chain and the HWND, but with the old count (measured: swap chain stays 4). `windowDestroyed` from the private render loop API deletes the window's render context (`cd->context`), so it cannot be reused; resetting the swap chain through private members would leave the render context and the layers on the old count.
- *Window swap works:* a new `QQuickWindow` with the new format, same screen, geometry, window states, flags, title, icon, colour, the window's filters (close, update gate, frame lock, fullscreen keys, focus release), graphics configuration and shared device; the scene's root item is reparented to the new `contentItem` (size follow and window-geometry watch reconnected), a new `PerfMonitor`, borderless re-applied, shown (fullscreen if the mode says so), then the old window is deleted. Measured for 4 → 1 → 2 → 8 → 4 → 1: swap chain has the requested count, client rect and fullscreen rect unchanged, an image resource, text and rectangles still draw, the scene accepts applies afterwards. Cost of a change: 16–21 ms for the call, 24–43 ms for the first pump (new QRhi, pipelines); the HWND is new (the window is recreated on screen once and becomes active).
- *Offscreen:* the plain `fromD3D11Texture(texture, format, size, sampleCount)` means "the texture is multisample". MSAA into the shared texture needs the overload with `QQuickRenderTarget::Flag::MultisampleResolve`: Qt creates a multisample colour texture and depth-stencil and resolves at the end of the pass (`ResolveSubresource` with the typed format of the QRhi texture, which D3D11 accepts for a typeless destination). The default format does not reach offscreen scenes; the render target alone decides. Verified per count 1/2/4/8 for `B8G8R8A8_TYPELESS` with UNORM bind, `R8G8B8A8_TYPELESS` with SRGB bind and `R16G16B16A16_FLOAT` (both through the linear pass: Qt resolves into its float source, the pass runs on resolved pixels): 0 edge pixels at 1, 352 / 572 / 814 at 2 / 4 / 8 (UNORM), 3 / 5 / 9 grey levels as expected for the standard pattern, interior and background exact. A count change is a rebind of the same scene (unbind, bind): verified 1 → 2 → 4 → 8 → 1 → 4, threaded render (default pool of 1).
- *Supported counts:* `QRhiD3D11::supportedSampleCounts()` is hard-coded `{1, 2, 4, 8}` (no device query); Qt clamps a request against that list and only logs a warning. `ID3D11Device::CheckMultisampleQualityLevels` on this device: 1/2/4/8 for `B8G8R8A8_UNORM`, `R8G8B8A8_UNORM`, `R16G16B16A16_FLOAT`, `D24_UNORM_S8_UINT`; 16 not. On OpenGL (Linux) QRhi queries `GL_MAX_SAMPLES`.
- *Layers follow the window:* a layer (`layer.enabled`, effect items, `ShaderEffectSource`, the snapshot of `grabToImage`) without `samples` renders with the render context's count (`QSGRhiLayer::grab`): in a window that is the window's count, so today every effect layer and snapshot in a window is rendered with 4× MSAA and resolved; offscreen scenes have count 1 there (`QQuickRenderControl::setSamples` is read only at `initialize`, at scene creation). `QQuickWindow::grabWindow` of a multisample swap chain gets a resolve inserted by QRhi (the grabs above).

**Cost** (medians; heavy scene of 2000 rotated 40×40 rectangles, 50 recoloured per frame, no VSync)

| Count | Window 1280×720 DIP (1920×1080 px): GPU ms / fps | QtTexture 1280×720: render_batch + readback ms (two runs) |
|---|---|---|
| None | 2.4 / 180 | 9.6 / 11.4 |
| X2 | 4.9 / 192 | 10.6 / 14.4 |
| X4 | 8.0 / 120 | 11.7 / 16.4 |
| X8 | 15.5 / 69 | 16.4 / 20.0 |

On this GPU 4× costs about 3.3× the GPU time of None in a window (today's default); the offscreen numbers include a constant CPU readback of the texture and vary by ±20 % between runs.

**Decided**
- **Window change:** QtNative replaces the `QQuickWindow` inside the same window handle (the window swap above, `window/window.cpp`); the C# handle, the node, the Qt items and their state stay. Rejected: `destroy()`/`show()` (keeps the count), private render-loop or swap-chain resets (render context and layers stay on the old count, private API), recreating the window from C# like VSync (all items are rebuilt by the reconciler: running Qt animations, video positions, focus and handler state are lost).
- **Default format:** no samples in `QSurfaceFormat::setDefaultFormat`; each window sets its count in its own format at creation.
- **Clamp:** natively, before Qt sees the count: the highest supported count not above the request, from `CheckMultisampleQualityLevels` on QtNative's device for the swap chain format (`R8G8B8A8_UNORM`) or the render target format (`R16G16B16A16_FLOAT` for the linear pass), on OpenGL from `QRhi::supportedSampleCounts()`; the export returns the count used so the node can warn. Qt's own clamp only logs.
- **Offscreen:** `fromD3D11Texture(…, sampleCount, MultisampleResolve)` in `bind`, also for the linear pass source; a change rebinds. Layers in a QtTexture stay single-sample (no `setSamples` on the render control: it would need a re-initialize).
- **Defaults per node (facts for the decision):** today windows have X4, QtTexture none. Qt Quick draws rectangles without vertex antialiasing (`antialiasing` is off for `Rectangle` without radius), so None makes rotated edges and thin diagonal lines visibly stair-stepped; X4 costs GPU time (table) and also makes every effect layer in the window multisampled. Decided by the user (2026-11-15): `Renderer` X4 (no visible change for existing patches), `QtTexture` None (no change either; Stride may antialias the final image itself); the issue's proposal was None for both.
- **Effect layers, snapshot, #117:** `layer.samples` stays out of scope. Snapshots and layers in a window keep following the window's count, offscreen they stay single-sample. The #117 feedback layer (recursive `ShaderEffectSource`) is never sampled as a multisample texture: in a multisample window Qt renders it into a multisample buffer and resolves into its two textures; `samples: 1` on it would decouple its cost from the window (not measured). A count change of a window with Clear off goes through `Scene::moveToWindow`, which releases the layer before the swap and restores it for the new window ("Clear pin", *Attachment*): the kept frame is lost and the first frame starts from the clear colour, as after a resize; on the software backend neither creates a layer.

**Implemented (tasks 2–4)**
- *Interface:* `vlqt_window_set_samples(w, requested)` returns the count used, `vlqt_window_get_samples(w)` the count of the swap chain (or of the format before the first show); `vlqt_offscreen_bind(…, samples, &usedSamples)` (`vlqt.h`). The clamp is `vlqt::device::clampSamples` (`device.cpp`): the highest count not above the request that QRhi lists and, on D3D11, that `CheckMultisampleQualityLevels` accepts for the target format and `D24_UNORM_S8_UINT`; without a QRhi the list 1/2/4/8. Measured: 16 → 8, 3 → 2.
- *Window* (`window/window.cpp`): created with 4 (`vlqt_window_create`); a window never shown only changes its format; a shown one gets the window swap (`replaceWindow`), an unchanged count changes nothing. The swap also carries the change count (`UpdateGate::continueFrom`), a pending close request and the perf overlay; the debug overlay is rebuilt under the new content item (`Scene::moveToWindow`); windows with the old one as transient parent get the new one; the new window is shown without activation unless the old one was active.
- *Texture* (`offscreen/offscreen_binding.cpp`): `bind` with `MultisampleResolve`, also into the linear pass source; a change of the count is a new bind.
- *Checked* (`--only Msaa`): real Win32 keys (WM_KEYDOWN through the WinForms loop, as in `KeyRouteTest`) reach the new HWND, it answers `WM_GETDLGCODE` (the filter looks the HWND up per message), a focused TextField keeps the active focus across a swap (typing goes on without a click); image, text, scene updates, window rect and fullscreen survive; offscreen 1/2/4/8 and the clamp for the three formats.
- *Not solved:* a snapshot in flight during a swap fails once ("the window was destroyed during the grab"; the next request works); pointer grabs and hover of the old window end with it, and the perf history restarts; the new HWND comes to the top of the z-order. Not tested: open `Popup.Window` popups and QML windows (transient parent moved), video items, OpenGL/Linux (the basic loop shares one GL context; another count may need another visual). Other Qt-created windows (`Popup.Window` popups, QML windows) lose the 4× of the former default format.
